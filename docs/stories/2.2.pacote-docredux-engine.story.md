## Story

**quero** o motor validado nos ex. 01–05 empacotado como `docredux_engine`, com LibreOffice configurável e imagem Linux,

1. Ex. 01–05 no container: 52→19, 34→14, 16→5, 26→12, 294→142 páginas; se a Carlito mudar alguma contagem, novo baseline registrado no `LOG.md` (Q13).
2. Cobertura ≥ 99,96%, 100%, 100%, 100%, 99,97% em qualquer caso (Windows e container).
3. `pyproject.toml` (Python ≥ 3.12, PyMuPDF 1.28.x, python-docx 1.2.x); módulos `ficha/`, `relatorio/`, `verify/`, `folha.py`.
4. LibreOffice achado por `DOCREDUX_SOFFICE` (fallback: PATH / caminho padrão do SO); `-env:UserInstallation` próprio por chamada (DT-5).
5. `python -m docredux_engine processar|folha` com saída JSON.
6. `render_docx` usa Carlito no lugar da Calibri (Q13).
7. Imagem base Linux (Python + LibreOffice da mesma linha do baseline do Windows + `fonts-crosextra-carlito` + `fonts-liberation`); a versão do LibreOffice do Windows registrada.

## Dev Notes

- Fonte da verdade do comportamento: `..\scripts\*.py` (acervo). O pipeline de hoje: `extract.py pdf out` → `render_docx.py out` → `soffice --convert-to pdf` → `verify.py pdf out`. Relatório: `render_relatorio.run` faz 2 passadas (sumário com paginação real, R42).
- Páginas da baseline = páginas do PDF do LibreOffice (não a estimativa de `verify.py`).
- `render_relatorio.py:23` tem `SOFFICE` fixo no Windows; `render_docx.py:17` tem `"fonte": "Calibri"`.
- LibreOffice do Windows: **26.8.3.1** (`soffice.com --version`, 2026-11-18). Debian não empacota a 26.8; a imagem baixa o `.deb` oficial da TDF para `x86_64` e `aarch64` (story 4.6 vai precisar das duas).
- Python local: só o `py -3.15` tem PyMuPDF 1.28.2 + python-docx 1.2.0. Container: Python 3.12.
